# core-rules

## 표준 작업 합의 (standing working agreements)

- 이 개발자는 명시적으로 요청하지 않은 변경(요청 범위를 벗어난 새 파일 대량 생성, 비요청 리팩터링, 임의의 스코프 확장)을 선호하지 않는다.
- 이 개발자는 가드·테스트·스크립트가 **쌓이기만 하는 것**을 싫어한다: 코드를 지우면 그 가드·테스트도 같은 커밋에서 지우고, 새 파일을 만들 땐 "무엇을 대체하나 / 왜 기존 걸로 안 되나"에 한 줄로 답할 수 있어야 한다. 답이 안 나오면 만들지 않는다.
- 이 개발자는 "테스트·검증을 실제로 실행하지 않은 채 '완료됐다'고 말하는 것"을 신뢰하지 않는다. 완료 주장은 실제 실행 결과(테스트 통과 출력, 명령 exit 0 등)로 뒷받침되어야 한다.
- 이 개발자는 추측으로 진행하기보다, 불확실하면 멈추고 확인받는 방식을 선호한다.

## 하네스 워크플로 (기본값)

- 이 개발자는 중간 규모 이상의 구현을 `/wook-plan`으로 시작해 수용 기준을 먼저 정하는 것을 기본 흐름으로 삼는다(그 기준이 `.claude/evaluate.recipe`가 되고, **커밋 시 게이트가** 그 기준으로 검증한다). 새 기능/모듈 구현 요청인데 `.claude/plan.md`가 없으면 코드 작성 전 `/wook-plan`을 먼저 제안한다(단순 수정/탐색/질문은 제외).
- 이 개발자는 새 함수·컴포넌트·쿼리를 만들기 전에, 프로젝트에 재사용 카탈로그(`.claude/reuse-index/`)가 있으면 거기서 기존 것을 먼저 재사용하는 흐름을 선호한다.
- 이 개발자는 재사용할 만한 함수·컴포넌트·쿼리를 새로 만들면, 카탈로그가 있는 프로젝트에서는 해당 도메인 `.claude/reuse-index/<domain>.md`에 한 줄(`이름 · 한줄설명 · path:symbol`)을 추가해 카탈로그를 최신으로 유지하는 흐름을 선호한다.
- 이 개발자는 프로젝트에 코딩 컨벤션(`.claude/conventions/`)이 있으면 해당 도메인 작업 시 `<domain>.md`(공통 규칙은 `shared.md`)를 따르며, 컨벤션을 새로 정하거나 바꾸거나 폐기하면 같은 작업 안에서 그 문서를 갱신해 최신으로 유지하는 흐름을 선호한다.
- 이 개발자는 독립 평가자(`wook-evaluator`, 예: `/wook-evaluate`)를 **비용에 맞춰** 쓰는 것을 선호한다(회당 7~12분): 훅·게이트·가드·deploy 등 **안전장치 자체**를 바꿨으면 항상(자기가 만든 검사기는 자기가 못 본다), 테스트가 못 잡는 체감 동작이면 보통, 문서·스위트가 덮는 기계적 리팩터면 생략. 부를 땐 **도메인에 맞게 실제로 굴리게** 하고(프론트=Playwright MCP, 백=엔드포인트, db=쿼리), 범위를 좁게 준다.
- 이 개발자는 프로젝트에 프로젝트 지도(`.claude/project-map.md`)가 있으면 앱을 실행·평가할 때 그 `Stack & Run`/`How to exercise`를 따라 띄우고, 프로젝트 구조·스택·실행/빌드/테스트 방법이 바뀌면 같은 작업 안에서 지도를 갱신해 최신으로 유지하는 흐름을 선호한다.
